## 二、断流自动切节点（对标桌面版 FailoverService）

### 实现
新增 02-java\patches\FailoverGuard.java（约 11 KB，仅依赖 java.* + org.json），编进 classes4.dex。

**工作方式**：
    BoxService 内核启动成功 → FailoverGuard.start()（零参数钩子，无寄存器冲突）
      每 20 秒：GET /proxies/{组}/delay?url=generate_204&timeout=6000
      连续 3 次失败（-1 / 超时）→ 遍历组内候选，逐个测延迟，选第一个能通的
           → PUT /proxies/{组} {"name":"节点"} 切换
           → 90 秒冷却，避免来回抖
    BoxService 会话结束 → FailoverGuard.stop()（两处清理路径都挂了）

- 只走 loopback HTTP（127.0.0.1:9091，回落 9090），不走 TUN、不改内核
- 组名自动发现：优先含「节点选择 / Proxy / PROXY」的 Selector，否则取第一个 Selector
- 候选自动排除 Selector/URLTest/Fallback/LoadBalance 组，只认真实节点
- API 不可用时静默待命，不报错、不重试风暴

## 三、踩坑记录

1. **VerifyError: register index out of range** —— concurrentEnabled() 改写时写了 .locals 0 却用 v0，verify 直接拒绝，app 连接时崩溃。改 .locals 1 解决。
2. **明文 HTTP 被系统拦截** —— FailoverGuard 访问 http://127.0.0.1:9091 一直返回 null（日志 clash api not reachable）。原因：Android 9+ 默认禁止 cleartext，manifest 没开 usesCleartextTraffic。补上后立刻可用。
3. **KernelSU 的 su 语法** —— su -c 能读文件但执行 iptables 报 Permission denied；su 0 sh -c 才行。

## 四、稳定性侦察结论（手机端还能做什么）

| 层 | 现状 | 可做 |
|---|---|---|
| 选节点 | sing-box urltest（3 分钟一轮，tolerance 150ms） | 缩短 interval / 降低 tolerance（属订阅侧参数） |
| 断流 | 本次新增 20 秒探测 + 3 连败切换 + 90 秒冷却 | 可加「吞吐低于阈值也切」（需流量统计） |
| 内核崩溃 | 已有 CoreRestartGuard（退避重启、会话结束复位） | 可加「重启后自动重连」 |
| 网络变化 | 未监听（WiFi↔蜂窝切换靠系统重连） | 可加 ConnectivityManager 回调，切换时主动重启内核 |
| 保活 | 前台服务 + VPN 服务 | 需确认电池优化白名单引导；HyperOS 上可加自启动引导 |
| 多内核 | 普通版内核写死 sing-box（全协议够用） | 不建议热备：TUN 重建必然闪断，收益低 |

> 结论：手机版稳定性的瓶颈不在「多内核」，而在故障感知速度和系统杀进程/网络切换。本次补上了前者的一半（断流感知），后者属于 Android 工程实践，可按需再做。
