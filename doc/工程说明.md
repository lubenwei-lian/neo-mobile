## 三、内核（`libbox.so`）

sing-box 内核以预编译动态库 `libbox.so`（约 81 MB）形式参与打包，JNI 桥接类为 `go.libbox.gojni`。

**该文件不随仓库分发**（体积大，且属于可替换的构建输入）：

- 构建前把自编译或配套的 `libbox.so` 放到 `01-apktool/lib/arm64-v8a/libbox.so`；
- 本地若保留过 `04-kernel/libbox.so`，可直接拷贝过去；
- 内核需要提供 `io.nekohasekai.libbox` 的导出，并支持配置中用到的出站类型。

其余原生库（终端、语法高亮、图形、Rust 扩展等）仍在仓库内，由 Git LFS 管理。

## 四、路径注意事项

`aapt2` 无法处理包含非 ASCII 字符的路径，**工程根路径必须是纯 ASCII**（父目录含中文也会失败）。

Windows 下可使用目录联接（junction）把工程根暴露为 ASCII 路径，例如：

```powershell
cmd /c mklink /J C:\neo_asc "D:\work\neo-mobile"
```

之后所有构建命令走 `C:\neo_asc\...`。

## 五、构建

依赖与命令见仓库根目录 `README.md`。核心流程：

1. 把补丁 Java（`02-java/patches`）编译为 class，再用 `d8` 生成 `classes4.dex`；
2. `apktool b 01-apktool` 重打包；
3. 把 `classes4.dex` 注入 APK；
4. `zipalign` 对齐、`apksigner` 签名；
5. 运行 `tools/verify-app.ps1` 与 `tools/verify-src2.ps1` 做产物校验。

推荐直接运行 `tools/build-app.ps1`（封装以上步骤并在失败时中止）。

## 七、签名与自校验

被测应用在 `Application.onCreate()` 中先执行完整性校验，失败会直接结束进程：

```
sget-object v0, Lio/nekohasekai/sfa/vendor/IntegrityCheck;->INSTANCE
invoke-virtual {v0, p0}, IntegrityCheck;->verify(Landroid/content/Context;)Z
if-nez v0, :cond_0
invoke-static {}, Landroid/os/Process;->myPid()I
invoke-static {p0}, Landroid/os/Process;->killProcess(I)V
```

`verify()` 取当前签名证书的 SHA-256，与内置 `REF[]`（XOR 0x5A 混淆）比对。

重打包并使用自己的 keystore 时，必须同步把 `REF[]` 换成新证书指纹，否则应用启动即退出：

1. 取 keystore 证书 SHA-256（小写、无分隔）；
2. 每字节 XOR 0x5A；
3. 按字节填入 `IntegrityCheck.smali` 的 `.array-data`。

## 八、已知限制

1. jadx 反编译收尾会报若干错误（非致命），与常规逆向结果一致。
2. `02-java/sources` 里的 Java **不可直接编译**：第三方库被 R8 移入默认包，部分应用内部类被改名；补丁编译以 `02-java/patches` 为准。
3. 重建包与原包**签名身份不同**：覆盖安装需先卸载原版（会清数据），或使用与原包相同的 keystore。
4. 未做反混淆。
5. 分发二进制需遵守上游 GPL-3.0 许可。
