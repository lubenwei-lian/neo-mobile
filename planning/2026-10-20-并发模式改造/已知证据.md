## 七、最终实现与实测（2026-10-21 00:10）

### 已落地的 5 项
1. **并发数量 5 → 8**：`POOL_SIZE` 字段 + `buildBalancer` 的 `pool_size` 字面量 + 日志文案，三处统一为 8；`DashboardViewModel` 退化路径截断 5 → 8。
2. **同地区筛选**：新增 `autoRegion`，把每个节点 `regionOf` 结果收集成 List，交给 `AutoRegionHelper.pickMost` 取出现最多的地区。实机 `selected_group_items={}` 时不再静默跳过。
3. **同协议筛选**：新增 `autoProtocol`，只在「已选地区内」统计协议类型，交给 `AutoProtocolHelper.pickMost`。
4. **用户自主选择**：移除 outbounds 重建时的 GROUP_TYPES 跳过逻辑 —— 原订阅 16 个 selector/urltest 组全部保留，用户可在节点页自由选节点；`route.final` 恢复为原订阅的「🐟漏网之鱼」。
5. **设置页开关**：新增「进阶 → 并发模式」点击行，点击切换并立即写入 Room（键 `concurrent_mode_enabled`）；`ensure` 入口门控，关闭时原配置原样返回。

### 附带修复
- **假节点过滤**：`collectNodes` 中跳过 `server` 为 127.0.0.1 / 0.0.0.0 / localhost / ::1 的提示节点（原池里混入「剩余流量：666.51 GB」「套餐到期：长期有效」）。

### 关键技术决策：为什么用 Java 助手类
手写 smali 做「计数取最大」两次失败（分支写反、寄存器复用），且 `apktool` 不报错、只在运行时静默失效。改为：
写 `.java` → `javac -encoding UTF-8` → `d8 --min-api 24` → 打包 zip → `apktool d` 反编译 → 得到干净 smali → 放入 `smali_classes3`。
`BalancerInjector` 只负责收集 List 并调用助手类，逻辑复杂度移出 smali。

## 八、第二轮修复（2026-10-21 01:30）—— 两个问题的真正根因

### 问题 1：设置页点开关「没反应」
【事实】上一轮做的是**纯点击行**（SettingsRow + 独立回调），**没有 Switch 控件、副标题被置空**。
点击实际有效（实测 DB 从 0x00 变 0x01），但界面上没有任何随点击变化的元素，所以看起来「没反应」。

【修复】改用 AppearanceScreenKt.ToggleRow（已改为 public），它自带 Switch 渲染。
踩了 3 个坑：
1. 不能新增独立 Composable —— 手写 startRestartGroup/endRestartGroup 导致 Start/end imbalance 崩溃
2. 不能用 v16+ 寄存器 —— invoke-direct / const/4 / move-object 单寄存器形式限 v0–v15
3. 必须复用「会话日志」那行的 v7..v14 槽位（v12 保持 composer），且不能污染 v6（后续 p(Z) 需要 Boolean）

回调类型必须是 Lzl2（invoke(Object)->Object，参数是新 Boolean），不是 Lxl2（无参）。

【实测】设置页出现「并发模式」+ 副标题 + 右侧 Switch；点击 Switch 本体后 DB 00 → 01。

### 问题 2：权重模式不生效
【根因链（三层）】
1. weightNodes 依赖 NodeDelayCache，但该缓存**只在点测速时才写入**
2. 写入路径不是我以为的 harvest（它收集 GroupItem.urlTestDelay，实际很少触发），
   而是 NodesScreenKt$NodesScreen$6$2$3$1$1$started$1 —— **每个节点测速完成的回调**里调 NodeDelayCache.record(tag, delay)
3. NodeDelayCache 是**纯内存 HashMap**，原 cleanupLegacyFile() 只删旧文件、不做读写 → App 重启即全丢

【修复】
- Java 写 DelayCacheStore（load/save 到 node_delays.json），javac+d8+apktool 生成 smali 放入 smali_classes3
- 测速完成回调里追加 NodeDelayCache.persist() → 每测一个节点落盘一次
- weightNodes 开头调 restoreDelaysIfNeeded() → 从文件回填内存缓存

【实测证据】
- 落盘文件生成：node_delays.json 2287 B，内容含真实延迟（AWS新加坡04:316ms, AWS日本01:391ms ...）
- **重启 App 后加权仍生效**：加权 入=10 出=33
- 配置加权分布（10 个唯一节点 → 33 个成员）：
    4份 × 7 个最快节点
    3份 × 1 个中档节点
    1份 × 2 个较慢节点

### 内核重复 tag 可行性（推翻上一轮的保守判断）
【事实】上一轮据 duplicate outbound/endpoint tag: 校验串判定「有加载失败风险」，未启用重复注入。
本轮实测：balancer 成员构造成 6:2:2 重复 tag（唯一 tag 只有 3 个），内核**启动成功**，
健康检查日志里同一 tag 出现多次，说明重复引用完全合法。
该校验串针对的是 **outbound 定义的 tag 唯一性**，不是 balancer 成员列表的引用。

【教训】上一轮的「风险判断」是错的，且没做实验就下结论 —— 应先花 5 分钟实测。
