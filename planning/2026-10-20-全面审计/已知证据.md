### 疑似逻辑颠倒 ★

## 二、★ 确证：缓存新鲜度判定颠倒（用 Java 原版对照）

### Java 原版（`02-java\...\SubscriptionUsage.java`，权威参考）
```java
private static final long REFRESH_INTERVAL_SECONDS = 1800;
...
jCurrentTimeMillis = System.currentTimeMillis() / 1000;
SubscriptionUsageInfo info = get(j);
if (!z2 && info != null && jCurrentTimeMillis - info.getFetchedAt() < REFRESH_INTERVAL_SECONDS) {
    return info;          // fresh=false 且 缓存存在 且 未过期(<30min) -> 直接用缓存
}
// 否则走网络探测
```
- `z`(z2) = 方法的 `fresh` 参数

### smali 实际（SubscriptionUsage.smali L2879-2911）
```smali
: L2879  if-nez v0, :cond_4        # v0=fresh; fresh==false 才继续  ✔ 与 Java 一致
: L2883  if-eqz v1, :cond_4        # 缓存存在才继续            ✔ 一致
: L2895  sub-long v10, v8, v10      # age = now - fetchedAt
: L2899  const-wide/16 v12, 0x708   # 1800 秒 (= Java 的 REFRESH_INTERVAL_SECONDS) ✔
: L2903  cmp-long v4, v10, v12
: L2907  if-gez v4, :cond_4          # age < 1800 -> 跳到 cond_4（不用缓存） ✗ 方向反了
: L2911  return-object v1            # 只有 age >= 1800 才 return 缓存
```

### 结论
Java 语义"**未过期就用缓存**"，smali 写成"**未过期就跳过缓存**"。
正确应为 `if-ltz v4, :cond_4`（age >= 1800 才去网络探测）。

### 造成的实际影响（与现象吻合）
- 只要缓存 < 30 分钟，**一律跳过缓存去网络探测**
- 网络探测失败（超时/被墙/临时错误）→ 返回 null → UI 显示 **"流量信息不可用"**
- 表现为"**明明缓存里有数据、诊断日志也显示抓取成功，UI 却显示不可用**"
- nano2 正是此情况：缓存有（fetchedAt 存在），但每次进页面都强制走网络

### 对照
| profile | 现象 | 解释 |
|---|---|---|
| nano2 | 流量信息不可用 | 缓存未过期却走网络，网络失败 → null |
| dasho.pqjc.site | 正常显示 | 网络探测成功，写回 Info |

## 四、lead 独立审计发现（第 2 个缺陷）

### 缺陷2：dedupByExit 注释与实现不符（"最快"未实现）
文件：01-apktool/smali/io/nekohasekai/sfa/bg/BalancerInjector.smali L639-694

**注释声称**（L642）：
\`\`\`
# 真并发去重：同一真实出口 IP 的节点只保留最快的 1 个
\`\`\`

**实际实现**：
- 遍历 List，用 HashSet 记录已出现的出口 IP
- \`HashSet.add(v4) -> v5\`；\`if-eqz v5, :de_end_skip\`（首次出现 v5=true -> 保留；重复 v5=false -> 跳过）
  ⇒ **方向正确**（去重本身没问题）
- **但全文无 NodeDelayCache 参与、无 Collections.sort / Comparator**（实测 grep 确认）
  ⇒ 保留的是**遍历顺序里第一个**，不是"最快的"

**连带影响（为什么值得修）**：
- 调用顺序（L3316-3324）：\`probeAsync\` -> \`dedupByExit\` -> \`weightNodes\`
- \`weightNodes\` 才读取 \`NodeDelayCache\` 做相对延迟加权
- 去重在加权**之前**，且不看延迟 —— 若同一出口的先出现者是慢节点，则快节点被丢弃，
  随后 \`weightNodes\` 只看到慢的那个 ⇒ **"快节点多份"的权重设计被削弱**

**严重度**：功能降级（非崩溃）。属"静默"类 —— 日志只体现 \`出口去重：入=N，出=M\`，看不出选错了谁。

**Java 对照**：\\\`02-java\\\` 中无 \`dedupByExit\`/\`NodeExitCache\`（jadx 版本早于该功能），
故此处**无权威对照**，判定依据是注释与实现的自相矛盾 + 调用顺序的客观事实。
标记：【验证过的推断】（代码事实确凿；"是否算缺陷"取决于原作者意图）

### P2：出口探测结果可能串号（lead 已独立复核 = 【事实】代码缺陷，但【不确定】实际发生）
证据（均为本次真实读取）：

- `NodeExitProbe\$handler.smali` L7-13：handler 是**无参构造**（不持有自己的 tag/latch）
- `handler.smali` L114：onResult 读**全局** `CURRENT_TAG`
- `handler.smali` L148：读**全局** `CURRENT_LATCH`
- `runner.smali` L95：每节点循环开始时覆盖全局 CURRENT_TAG
- `runner.smali` L129：`await(6, SECONDS)` —— **超时无判定**，直接 L138 清空 latch、L140 进入下一节点
=> 迟到的 STUN 响应会写进**下一个节点**名下。
