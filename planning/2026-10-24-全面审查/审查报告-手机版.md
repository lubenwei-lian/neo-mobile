### P0-2 SubGuard.prepare() 改写订阅后没有"原文回退重试"，且无条件删除 dns.fakeip

**现象**
- 订阅正文在 checkConfig 之前被 prepare() 改写成新 DNS 格式；若改写"成功"但内核仍拒绝，代码直接抛错，不会拿原始正文再 checkConfig 一次，用户侧表现是"这个订阅永远更新失败"。
- 迁移器把顶层 dns.fakeip 无条件 remove（即使 servers 里没有 fakeip 项），fakeip 配置会静默消失。

**证据**
- 02-java/patches/SubGuard.java:159-172：prepare() = migrate() → check() → throw / return migrated；没有 check(migrated) 失败后 check(content) 的分支。
- SubGuard.java:281：dns.remove("fakeip")（无条件）。
- SubGuard.java:287-289：route.put("default_domain_resolver","local")，假定配置里存在 tag=local 的 DNS server；不存在时 sing-box 1.12+ 会报 default domain resolver not found。
- 接线点：SubscriptionFetcher.smali:317（后台更新，异常被 :343 的 catch Ljava/lang/Exception 捕获，转为 Outcome 失败）；DashboardViewModel$updateProfile$1.smali:494（try 块由 :866 的 .catch Ljava/lang/Exception 覆盖，转成 Failed to update profile: …）。
- 现网订阅（本机场）不会触发：03-dist/probe3/old.json 的 dns.servers 第 2 项是 {"address":"local","tag":"local"}；probe3/new.json 已是新格式 {"type":"local","tag":"local"}。所以这是条件触发的代码级确证，不是已在现网复现的事故。

**建议修法**
1. prepare()：migrated 失败后回退 content 再 check 一次；两次都失败才抛，错误信息带"迁移后/原文"两种原因。
2. 迁移前校验：若 route.default_domain_resolver 不存在且没有任何 tag=local 的 server，则不要写 "local"（或补一个 {"type":"local","tag":"local"}）。
3. dns.fakeip 只有在"确实有 server 迁成了 fakeip"时才 remove；否则保留并记日志。
4. 给 prepare() 加"迁移结果不等于原文"的日志（当前只在成功时打"订阅 DNS 已从 legacy 迁移为新格式"，SubGuard.java:290）。

**风险**：把"机场下发老格式"从"客户端能用"变成"客户端永久更新失败"，且失败信息是内核的英文报错，用户无法自查。

### P1-2 FailoverGuard.start()/stop() 竞态会产生两个探测线程

**证据**
- FailoverGuard.java:44-60：start() 只判断 running，然后 new Thread 覆盖 worker，无同步、无 join。
- :62-71：stop() 把 running=false 后 interrupt()，不 join。
- :91-105：loop() 里 while(running) + sleep(INTERVAL_MS)；线程若正在 http() 读 socket（readTimeout 最多 6-8 s），interrupt() 不会中断它；返回后 running 可能已被下一次 start() 置回 true → 旧线程继续循环，而 worker 已指向新线程，旧线程再也无法被 stop。
- BoxService 每次连接/断开都会 start()/stop()（:2158/:2939/:3300），快速重连即可触发。

**后果**：两个线程各自维护 fails 计数、各自 PUT /proxies/...，切换次数翻倍、日志交错；线程是 daemon，泄漏不可见。
**修法**：start() 用 synchronized + if (worker != null) return;；stop() join(3000)；或用 AtomicInteger generation，loop 每轮检查 gen == myGen。

### P1-4 冷却/找不到节点时 fails 不清零 → 每 20 秒全量串行探测

**证据**：FailoverGuard.java:144-158。fails >= 3 后：冷却中 continue（:150-152）不重置 fails；target == null 也 continue（:155-157）不重置。此后每一轮都会进 pickHealthy()，而 :350-362 对组内每个候选串行发 /delay?timeout=4000（readTimeout 6 s）。20 个节点最坏 120 s，导致探测周期被拉长、日志刷屏、流量浪费。
**修法**：冷却/无目标时设 fails = 0（或降到阈值以下），并给 pickHealthy 加总预算（如 15 s）与"本轮最多测 K 个"。

## 架构风险与重构建议（smali 收敛方案 + 工作量）

### 现状结构风险

1. 手工 smali 是主线：16 个 M smali 里只有 4 个是"一行 Java 调用"（BoxService×3、SubscriptionFetcher、DashboardViewModel、SubscriptionUsage），其余 12 个是手写逻辑（BalancerInjector 86 KB、NodesScreenKt、HomeScreenKt、Settings、ProfileManager、EditProfileViewModel…），没有任何 Java 源码对应（02-java 只覆盖补丁类和 src2）。
